# 复试高频追问与回答要点

回答时先给结论，再结合代码或报告举证。不要背长句，也不要夸大为“全网首创”。

## 1. 这个项目的创新点是什么？

它不是提出新的 GIS 算法，创新点主要在问题定义和工程整合：把 `.aprx` 的工程级风险统一为稳定 finding、可配置策略、健康评分和基线差异，并同时接入命令行、ArcGIS Pro Python Toolbox 和 CI。更准确的表述是“面向 ArcGIS Pro 交付质量的开源工具探索”。

## 2. 和 ArcGIS Pro 自带检查或打包功能有什么区别？

内置功能通常服务于某个具体工作流。Guardian 提供的是跨项目的统一规则层：检查结果可以保存为 JSON、进入版本比较、按团队策略决定是否阻断，并生成适合交付的 HTML 报告。它不是替代 ArcGIS Pro，而是在交付流程外层增加可重复的质量门禁。

## 3. 为什么坚持只读，不直接自动修复？

质检工具如果自动改路径或保存工程，会改变被检对象，而且错误修复可能造成更大风险。当前设计把发现与修复分离：先给出证据和建议，由用户确认后再在副本中处理。这也让审计结果更容易复现。

## 4. 健康分是否客观？

它不是绝对质量真值，而是一个确定、透明的风险摘要。不同严重级别对应固定扣分，团队可以通过策略调整严重级别。真正用于门禁的是 finding 与阈值；分数主要用于快速比较和趋势观察。

## 5. 基线差异如何保持稳定？

每条 finding 使用检查代码和上下文生成稳定指纹。当前报告与历史 JSON 按指纹集合比较，从而得到新增、解决和未变化问题。项目路径脱敏不会改变已经生成的指纹。

## 6. 为什么 After 还有两条绝对路径信息却是 100 分？

本案例是单机复试演示，公开策略把 `ABSOLUTE_SOURCE_PATH` 降为 info，info 不扣分，但报告仍保留提示。生产环境可以把它设为 warning 或 error，并限制允许的数据根目录。策略文件和报告同时公开，因此不是隐藏问题。

## 7. 你是怎么测试的？

核心模块通过模拟 ArcPy 对象测试数据源分类、finding、评分、基线差异、HTML 转义和策略行为；真实 `.aprx` 使用 ArcGIS Pro 自带 Python 运行；HTML 报告还检查了桌面与手机视口、控制台报错和横向溢出。GitHub Actions 负责运行不依赖 ArcPy 的测试。

## 8. 项目的主要局限是什么？

它只读取保存状态，不检查未保存的界面修改；只检查结构和元数据，不判断要素内容是否正确；不会主动访问需要认证的服务；当前兼容性验证主要基于 ArcGIS Pro 3.0.1；也没有自动修复功能。

## 9. 如果网络数据源暂时不可用，会不会误报？

报告只表达“审计机器在当时无法解析该数据源”，不会声称数据永久丢失。团队可以按环境把相关检查设为 warning，并在网络恢复后重新审计。

## 10. 为什么核心模块不在导入时直接依赖 ArcPy？

ArcPy 只存在于 ArcGIS Pro 环境。如果所有逻辑都和 ArcPy 强耦合，普通 CI 无法运行测试。通过依赖注入，真实运行传入 ArcPy，测试传入模拟对象，评分、策略和渲染逻辑就能在通用 Python 环境验证。

## 11. 是否使用了 AI？

按真实情况回答。稳妥的表达是：“我使用 AI 辅助脚手架、代码检查和文档整理，但需求定义、结果验证和关键设计取舍需要我确认。我能现场解释审计流程、策略、基线指纹和测试方法。”如果这些部分还解释不清，先学习和实跑，不要声称已经掌握。

## 12. 下一步准备怎么做？

优先级可以是：增加规则插件接口；覆盖更多 ArcGIS Pro 版本；加入项目打包前后对比；提供结构化 SARIF 或 PR 注释；积累真实团队项目的误报与漏报数据，用数据校准规则和权重。
